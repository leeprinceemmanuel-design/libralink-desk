Well-Architected review

The six pillars of the AWS Well-Architected Framework, used twice: once when the first deployment worked (to decide what to build next), and again after the incident was fixed.

Our deliberate trade-off. We optimised for Security and Operational Excellence. We accepted a weaker Reliability design: one EC2 instance in one Availability Zone, with MongoDB on the same server. A second server, a load balancer and a managed database would roughly double the cost and the moving parts for a class-sized assistant. We cover the risk with hourly backups and a restore we have actually timed.

Pass 2 — after the incident (9 November 2026, evening)

Operational Excellence — good

The framework asks: run and monitor the workload, automate changes, learn from failures. We do: a dashboard and 12 alarms e-mailing both of us; every answer logged with its timing, result and version; two automations running unattended; a real incident with root cause, prevention and a runbook. Still weak: code changes reach the server by a manual git pull and restart, not automatic deployment.

Security — good

The framework asks: strong identity, least privilege, protect data in transit and at rest, keep an audit trail. We do: own AWS login and MFA for each person (the Free plan blocks IAM console users, so we use AWS's Team page), least-privilege roles for machines, no access keys anywhere; secrets in Parameter Store; HTTPS for users; server reachable only from CloudFront, no SSH port; encrypted disk and bucket; CloudTrail on (GuardDuty is blocked on our Free plan). Still weak: the hop from CloudFront to the server is plain HTTP inside AWS's network.

Reliability — adequate (accepted)

The framework asks: recover from failure automatically, test recovery, avoid single points of failure. We do: hourly backups to S3 with a tested restore (RTO 30 seconds measured for the database, RPO up to 1 hour), Docker restarts crashed containers, systemd restarts the stack after a reboot, the health check notices outages from outside, log rotation prevents a full disk. Accepted gap: one server in one Availability Zone.

Performance Efficiency — adequate

The framework asks: right-size resources using data. We do: we measured memory (48% average over 6 hours, 72% highest) and CPU (about 1–2% on the dashboard, with a short rise at start-up) under our test load, and kept t3.small, because memory never came near our 90% alarm; the larger Free Tier size (c7i-flex.large, 4 GB) would only be needed if it did. Average answer time 2.4 s, mostly spent waiting for the model. Still weak: no load test with many users at once.

Cost Optimization — good

The framework asks: pay only for what you use and know where the money goes. We do: a USD 30 monthly budget on the real cost (free credits excluded) with e-mails at 50/80/100% — fixed on 14 Nov, because the first version counted the credits and its e-mails were never verified; every resource tagged Project=SAM10, Team=libralink; the model is on a free tier; CloudFront instead of a paid load balancer; backups expire after 8 days. Cost per day: USD 0.818 for the bare server, IP and disk → USD 0.820 with all the improvements (10–12 Nov). Still weak: the Elastic IP and instance cost money even at night when nobody uses the system.

Sustainability — good

The framework asks: the same results with a smaller footprint. We do: one small instance, no idle extra servers, the AI model shared on the provider's hardware instead of a GPU of our own, short log retention, conversation search (Meilisearch) switched off because nobody needed it. Still weak: the server runs 24 hours a day.

The one gap we would fix first

Reliability: the single server. Everything else on this page is "good enough" for a class project, but if our one instance or its Availability Zone fails, users get nothing until we rebuild — 30 seconds to restore the database (measured) plus launching and setting up a new server, which we have not timed end to end. The first fix is cheap: an EC2 Auto Scaling group of one instance with a launch template that runs our bootstrap script, so a dead server is replaced automatically; MongoDB data would move to a separate EBS volume with snapshots (or to a managed MongoDB-compatible database). That turns "we restore by hand" into "it heals itself".
