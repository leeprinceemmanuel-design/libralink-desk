AWS infrastructure design

Where every part of LibraLink Desk runs, and how one question travels from the user to the AI model and back. One region, one server, one database — on purpose.

Why Sydney, not Singapore? Singapore is closer to the Philippines and was our first choice (and our midterm design). But our AWS Free-plan account is locked to one region by AWS's own rules: on 9 Nov 2026 we tested creating an S3 bucket, a parameter, an SNS topic, an EC2 server (dry run) and listing Lambda functions in three regions. All were denied in Singapore and us-east-1 and allowed only in Sydney (ap-southeast-2). The cost is a little extra delay for users in the Philippines, which is small next to the AI model's answer time.

Solid arrows: the path of a question (numbers match the list below). Dashed arrows: operations traffic — content and backups, secrets, metrics and logs, alerts.

How a question travels

  1. Browser → CloudFront (HTTPS). The user opens the …cloudfront.net address. CloudFront holds the free HTTPS certificate and forwards every request (no caching, because every chat is different).
  2. CloudFront → nginx on EC2 (port 80). The security group only lets in CloudFront's own address list, so nobody can reach the server directly. nginx adds the LibraLink theme and logo to the page and writes one log line per request.
  3. nginx → LibreChat. LibreChat checks the user is logged in. Because our model spec is enforced, every chat uses the LibraLink Desk preset: our rules plus the whole library handbook, which the server downloaded from S3 when it started.
  4. LibreChat → Google Gemini (HTTPS) and back. The question and the handbook go out to Gemini, outside AWS. The answer streams back word by word through nginx and CloudFront to the browser.
  5. LibreChat → MongoDB. The question and answer are saved. Every minute the request logger reads new answers and writes one JSON line each (question, time taken, success, model and content version) to /libralink/requests in CloudWatch.
