LibraLink Desk: a library help desk that answers any time — and is run properly

An AI assistant for the (invented) Luntian Ridge University Library. It answers questions about opening hours, borrowing, fines, rooms and e-resources from the library's own handbook, and sends people to the right desk for everything else.

Executive summary (plain English)

What the system does

Students and staff open a web page, sign in, and type a question such as "How many books can I borrow?" or "Where do I pay a fine?". The assistant answers in a few sentences, using only the library handbook we wrote, and says which section the answer came from. If the handbook does not cover the question, it says so and names the desk to ask. It never looks up anyone's account and never decides anything about a person — for example, it cannot waive a fine.

We did not build the chat program from scratch. We took LibreChat, a popular open-source chat application (MIT licence), and reskinned it: new name, logo, colours, wording, our own handbook, and our own rules. The "brain" is Google's Gemini model, reached over the internet; we do not run the model ourselves. Everything else — the server, storage, security, monitoring, backups — runs in our AWS account in Sydney (ap-southeast-2).

What was wrong with how it was run at first

The first version worked, but nobody would want to rely on it. It ran on plain HTTP with the server open to the whole internet, nobody would have known if it crashed or filled its disk, there were no backups, and logs could grow until they filled the disk. Details are on the Baseline page.

What we changed

  • Safer access: HTTPS through CloudFront; the server only accepts traffic from CloudFront; no SSH port at all; each of us signs in with our own AWS login and MFA, with no shared logins and no access keys.
  • No secrets in code: the AI key and encryption keys live in AWS Parameter Store and are read when the app starts.
  • We can see it working: a dashboard and 12 alarms, including ones that notice when the system is "up but useless" (failed, empty or "not found" answers).
  • We can get it back: the database is backed up to S3 every hour and we actually restored it and logged back in.
  • Less manual work: backups and an outside health check run on their own.
  • We broke it on purpose and fixed it for good: we filled the disk, the alarm warned us 4 minutes later (2 minutes before users noticed), we found the cause (a log file with no size limit) and added log rotation so it cannot happen the same way again. The test also uncovered two hidden problems, which we fixed or listed as next steps.

What improved

Measured on our own account, 9–14 November 2026: a full disk is now detected in 4 minutes (before: never); the site was up for 99.8% of 473 outside checks (the one failure was our own test); 118 of 120 hourly backups succeeded and a restore takes 30 seconds; the assistant scored 30/30 on day 1 and again on day 5, answering in 2.4 s on average; and all of this costs USD 0.002 a day more than the bare server (USD 0.82 a day in total). See Results.

Trade-off we chose: we optimised for Security and Operational Excellence and deliberately accepted a weaker Reliability design — one server in one Availability Zone, so if that zone fails the service is down until we rebuild it from backups. For a class-sized library assistant, that is cheaper and simpler, and our tested restore keeps the damage small. See the Well-Architected review.
